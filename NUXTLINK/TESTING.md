# NuXT Link 4.1 release checks (19 October 2026)

The 4.1 Linux client prefers LZ4 to heatshrink only at 115200 baud and 4096-byte blocks, and only when the LZ4 packet is at most 512 bytes larger. A local A/B test against the physical NuXT used the existing wire-v8 DOS server, RTS/CTS, unique temporary DOS names, staged upload readback, and an independent DOS file CRC. Every reported run had zero retries. The executable was also downloaded and checked by SHA-256 after the initial pair and the 512-byte run. These times include DOS verification and commit:

| Source | 4.0 smallest-packet choice | 4.1 LZ4 preference |
|---|---:|---:|
| 367,760-byte DOS executable | 57.12–57.23 s | 41.83 s |
| 256 KiB mixed disk-image slice | 40.65–40.68 s | 31.85 s |

A separate 57600-baud A/B test temporarily enabled the same preference for the mixed slice. It took 57.50 s with the old choice and 49.36 s with LZ4, with zero retries and matching DOS CRCs. The 4.1 default still applies only at 115200/4096; slower baud rates may lose that gain as the extra bytes take longer to send. No physical 9600-baud A/B test was run. The 4.1 DOS executable changes only its startup version label and retains wire version 8.

The 4.1 DOS rebuild is 27,894 bytes and differs from the 4.0 binary in one banner byte. The Linux suite ran 96 tests: 75 passed and 21 Tk widget tests were skipped because no display was available. A disposable QEMU/MS-DOS 6.22 image passed zero, mixed, and random upload/download roundtrips, explicit LZ4 decoding, and malformed zero-run recovery. The physical A/B tests used the wire-compatible 4.0 DOS binary; the new 4.1 banner has not been started separately on the NuXT.

## Earlier 4.0 checks

The 4.0 promotion changes the DOS executable name and banner, Linux title and profile store, but retains serial wire version 8 and the 0.3.2 transfer logic. On the physical NuXT, a 128 KiB random file upload was deliberately stopped after 16 KiB. A new serial connection resumed at exactly 16,384 bytes, finished the upload, downloaded the file, and matched every byte against the source SHA-256 (`e40c632817f9369c6ea1ced3006503147bd1b15c20592f57f9ffd5e038bdaca5`). The unique test file was then removed from DOS. This used the 0.3.2 preview binary; the rebuilt 4.0 binary still requires a final physical startup check.

The 4.0 `NUXFER.COM` rebuild used Open Watcom's 8086 target with warnings as errors and is 27,894 bytes. Its Linux suite ran 95 tests: 74 passed and 21 Tk checks were skipped because this environment had no display. A migration test imported both previous serial profile stores, preserved a conflicting older name under a suffix, skipped a LAN profile, and verified that saving a new profile did not alter either source file. A disposable QEMU MS-DOS 6.22 run booted the 4.0 DOS binary and passed exact upload/download roundtrips for zero, mixed, random and `MATRIX.IMG` data, explicit LZ4 decoding, and malformed zero-run recovery. These checks do not replace the final startup test on the physical NuXT.

Open Watcom built `NUXFAST.COM` for 8086 with warnings treated as errors. The host suite ran 94 tests: 73 passed and 21 Tk widget checks were skipped because this environment had no display. Five focused checks cover normal Linux download commits, no-clobber behavior, rollback when metadata saving fails, and the backup-copy fallback where hard links are unavailable. A native cross-check ran the DOS LZ4 decoder against 39 compressed blocks at boundary lengths, plus malformed input. The LZ4 and LZO research encodings were also decoded byte-for-byte using their system libraries before comparison.

A disposable copy of the local MS-DOS 6.22 test image booted `NUXFAST.COM` under QEMU. At negotiated 115200 baud and 4096-byte blocks, the Linux client uploaded and downloaded three synthetic files plus `MATRIX.IMG` and checked exact readback plus DOS whole-file CRC:

| File | Original bytes | Upload payload | Download payload |
|---|---:|---:|---:|
| Zero-filled | 131,072 | 960 | 1,124 |
| Mixed zero/random/text | 73,732 | 24,958 | 49,563 |
| Random | 8,193 | 8,193 | 8,202 |
| MATRIX.IMG | 1,474,560 | 29,429 | 33,419 |

An explicit LZ4 upload completed DOS staging readback and download with matching bytes. A malformed zero-run upload was rejected, and the following valid block completed a staged upload, confirming that the bad packet did not advance the file. These payload counts exclude frame headers, ACKs, retries, and verification traffic. QEMU's PTY does not represent the NuXT's CPU, UART, disk, or FTDI timing; the reported roundtrip seconds are not a throughput claim.

The owner and Codex tested the physical NuXT V20, CF drive, COM1, 16550 FIFO, and FTDI cable at 115200 baud with RTS/CTS. Codex drove the Linux client while the owner started the DOS server. With the new decoder, the full 1,474,560-byte `MATRIX.IMG` uploaded in 60.96 seconds, sending 29,429 data-payload bytes. Data transfer and DOS staging took 41.18 seconds; the DOS staging readback took another 19.60 seconds. A separate DOS file-hash query agreed with the upload CRC16. There were no retries or new CRC, overrun, framing, or flow-timeout errors. The earlier 8 KB-frame experiment with the original bytewise decoder took 87.63 seconds for the same image, despite fewer requests. This comparison changes both the decoder and frame size, so it is evidence for a faster complete build rather than a precise isolated decoder benchmark.

A 262,144-byte slice of mixed `COMPRESS.BIN` uploaded in 23.78 seconds with 132,928 data-payload bytes. DOS staging readback and a separate file-hash query agreed. The diagnostic error counters did not increase. The client counted one retry while discovering a server left at 115200 baud; the transfer itself completed. The older decoder with the 8 KB frame took 26.12 seconds for this same slice. On that older build, raw transfer took 33.38 seconds, so compression was helpful for this data. The previous 4 KB-frame preview also uploaded and downloaded the full 1 MiB mixed file and a 41 KB DOS executable with exact SHA-256 readbacks; those two files have not been repeated with the 0.3 DOS binary.

The owner also ran the 0.3 Linux GUI with the physical NuXT at 115200 baud and 4096-byte blocks. Four 5,046,272-byte queues completed in each direction with no failed jobs: `MATRIX.IMG`, `SIMCITY.IMG`, `COMPRESS.BIN`, and `SOLID.BIN`. The 1 MiB solid file took about 2m 12s to upload and 2m 19s to download; `MATRIX.IMG` took about 1m to upload and 43s to download. Lowering the FTDI latency to 2 ms did not materially change these times. The GUI's CRC checks passed, but those four GUI transfers were not separately compared byte-for-byte outside the protocol. The DOS diagnostic counters from one server session showed 94 framing and 94 break flags, with no CRC, overrun, parity, or transmit-timeout count; these are flags rather than 188 distinct events.

For 0.3.2, the DOS readback and file-hash scans process up to 8 KB per request through the same 4 KB buffer. A disposable QEMU scan of `MATRIX.IMG` used 180 requests instead of 360 and took 0.188/0.181 seconds in two optimized runs versus 0.221/0.212 seconds for 0.3.1. That is a small emulator improvement, not a prediction of NuXT speed. The 0.3.2 executable is 27,902 bytes, 16 bytes larger than 0.3.1; its static buffer sizes are unchanged. The host suite passed 73 tests with 21 Tk checks skipped, and a QEMU DOS roundtrip passed zero-filled, mixed, random and `MATRIX.IMG` upload/download, explicit LZ4, and malformed zero-run recovery.

The owner then showed the 0.3.2 Linux GUI completing four-file queues in both directions on the NuXT, 5,046,272 bytes per queue with zero reported issues. The DOS file pane showed the 27,902-byte `NUXFAST.COM`. Download times were about 2m 19s for each 1 MiB BIN, 1m 49s for `SIMCITY.IMG`, and 43.2s for `MATRIX.IMG`; upload times were 1m 12s, 2m 12s, 2m 03s, and 1m 00s respectively. The 0.3.2 DOS verification phase was not timed separately, so these totals do not establish how much the larger scan step saved. On Linux, the resulting `MATRIX.IMG` matches a previously established SHA-256, and `COMPRESS.BIN` and `SOLID.BIN` match separate local source copies by SHA-256. The screenshots alone do not prove which DOS process was running, but they show the matching executable present.

A further disposable QEMU/MS-DOS run with the 0.3.2 binary passed 2048- and 4096-byte transfer blocks, lost ACKs, corrupt replies, sequence wrap, interrupted upload and download resume across block-size changes, invalid compressed frames, cancelled DOS staging readback, preservation of the old destination, and empty-file verification. Its integration test now expects the first readback step to advance 8 KB. Before promotion, a physical interrupted-transfer/resume test would add the most useful coverage. An archive and DOS date/time sync are secondary hands-on checks. The 8086 compile target and QEMU runs do not establish speed on an 8088; the physical measurements above are for the NuXT V20.

To repeat the focused emulator check from this package, run `python3 tests/qemu_roundtrip.py`. Set `NUXTLINK_DOS_IMAGE` to your own raw DOS test image with its FAT partition at byte offset 8704 if the development image is unavailable. The test copies its input into a temporary directory and does not touch physical drives or serial ports.
